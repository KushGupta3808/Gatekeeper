# Load Test Results

**Date:** August 2026
**Tool:** Locust
**Target:** GateKeeper gateway, `token_bucket` algorithm, capacity=5, refill=1/sec
**Test config:** 30 concurrent simulated users, ramped up at 10 users/sec, run for 15 seconds

## Command used

```bash
locust -f locustfile.py --host http://localhost:8000 \
    --headless -u 30 -r 10 -t 15s \
    --csv=docs/load_test_results --html=docs/load_test_report.html
```

## Results

| Metric | Value |
|---|---|
| Total `/api/data` requests | 1,400 |
| Requests allowed (200) | 540 (~39%) |
| Requests rate-limited (429) | 860 (~61%) |
| Genuine system failures (502/503) | 0 |
| Median latency | 2 ms |
| p95 latency | 6 ms |
| p99 latency | 23 ms |
| Max latency | 30 ms |
| Sustained throughput | ~93 req/s |

## Interpretation

**Zero genuine failures** across 1,400+ requests under concurrent load confirms the rate limiter is holding correctly - every rejection was a deliberate, correct 429, not a crash or an unhandled error.

**~61% of requests being rate-limited is expected, not a problem** - with 30 clients each capped at a burst of 5 and a slow refill rate (1 token/sec), and Locust firing requests as fast as it's configured to (0.1-0.5s between requests per simulated user), most requests were always going to arrive faster than tokens could refill. This is the rate limiter doing exactly its job under aggressive load, which is the scenario it exists to handle.

**Latency stayed low even under load** - p95 at 6ms means the Redis-backed Lua script (the atomic check-and-decrement operation) adds negligible overhead even with 30 concurrent clients hammering it simultaneously. The gap between p95 (6ms) and p99/max (23-30ms) suggests occasional slower requests under contention, worth investigating further if this were a production system (likely Redis connection pool behavior under concurrent load).

## How outcome counts were obtained

Locust's own failure tracking was deliberately configured to treat HTTP 429 as a **success** (see `locustfile.py`), since a rate-limit rejection is correct behavior, not a bug - counting it as a "failure" would make a correctly-functioning system look broken in the report.

To get the actual allowed vs. rate-limited breakdown, the gateway's own `/metrics` endpoint (built in Stage 6) was queried directly after the test:

```bash
curl http://localhost:8000/metrics | grep gatekeeper_requests_total
```

```
gatekeeper_requests_total{outcome="allowed"} 540.0
gatekeeper_requests_total{outcome="rate_limited"} 860.0
```

This is a nice validation that the observability stack (Stage 6) and the load testing stage (Stage 7) work together as intended - Locust proves the system holds up structurally, and Prometheus metrics provide the ground truth on what actually happened, which Locust's own success/failure framing can't fully capture on its own.
